# 待查：偶发的单刻尖峰（可能是 Java 自身的停顿）

记录日期：2026-11-02。状态：**未确认，暂不处理**。

> 2026-11-14 注：下面的数字是寻路还在主线程上时测的。之后寻路放到了后台线程（`PERF_BACKLOG.md` 第 4 项），主线程只复制区块，“每刻 8 毫秒”的上限已经不存在。要查的话先重新测一遍，看这些尖峰还在不在。

## 现象

压尖峰（开服预热 + 寻路守住每刻 8 毫秒）之后，大部分场景里机器人单刻最长只有 8～10 毫秒，但下面几个场景还会冒出**一刻** 15～39 毫秒：

| 场景 | 内容 | 单刻最长 | 其中寻路 |
|---|---|---|---|
| H3 | 从 y=0 的矿洞爬到地面 | 39.4 ms | 39.3 ms |
| W19 | 水下挖沙砾拿燧石 | 37.3 ms | 37.2 ms |
| W24 | 顺着瀑布往上爬 | 23.1 ms | 23.0 ms |
| W26 | 冰下抓鱼 | 18.6 ms | 18.5 ms |
| V2 | 从矿洞回到 300 格外 | 41.0 ms | 15.5 ms |

特点：每个场景通常只有**一刻**这么长，不是反复出现；平均耗时（0.1～8 毫秒/刻）完全正常。

## 为什么怀疑是 Java 自己

- 寻路现在每 16 个节点就看一次表，超过 8 毫秒就停，一刻里正式规划和预规划共用这 8 毫秒。单个节点的计算要慢到 30 毫秒，代码里找不到这样的地方。
- 计时用的是挂钟时间（`System.nanoTime()`）。如果那一刻正好碰上 **垃圾回收（GC）停顿** 或 **即时编译（JIT）**，整段停顿都会被算到"寻路"头上。
- 只出现一次、位置不固定，也符合 GC 的特点。

## 怎么确认

1. 测试服启动时打开 GC 日志：在 `scripts/run-scenarios.ps1` 启动 Java 的参数里加上
   `-Xlog:gc*:file=run/gc.log:time,uptime`
2. 让 `Perf` 在某一刻超过 12 毫秒时往日志里写一行"慢刻"，带上时间。
3. 跑一遍全部场景，对照两份日志的时间点：
   - **慢刻都正好撞上 GC 停顿** → Java 的问题，不用管（真服务器可以调 GC 参数，比如加大内存、换成 ZGC，那是服务器配置的事）；
   - **对不上** → 是我们的代码，再在寻路里细分计时（建图、估算换气、查地表高度等）找出是哪一段。

## 影响

一只机器人时几乎无感（一刻偶尔慢几十毫秒）。如果以后每人一只，而且真是我们的代码，十只的尖峰撞在一起才会明显。到做"多只机器人"之前查清楚即可。
